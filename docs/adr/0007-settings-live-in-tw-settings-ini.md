# 0007 — Settings live in `tw_settings.ini`, in the working directory

**Status:** Accepted (jc-33) · **Amended** (jc-40, to state where the file actually is) · **Applies to:** `settings.cpp`, `tworld.c` `initdirs()`, `package.ps1`

## Context

Upstream Tile World keeps its settings in `save/settings`, an extensionless file inside the
directory where solution files go. That is invisible to a Windows player, unopenable by
double-click, and mixed in with data they must not delete.

The name `settings.ini` was not available: SuperCC — the other half of this maintainer's toolchain,
often installed in the same folder — used it first. SuperCC moved to `succ_settings.ini` in its
jc-8 specifically to free up the generic name, and this fork took `tw_settings.ini`.

## Decision

**Settings are a plain `name=value` INI file called `tw_settings.ini`.** Its parser is deliberately
forgiving in some ways and deliberately strict in others, and the differences matter:

- **Section headings are decoration.** A setting works the same wherever it sits. (This is the
  opposite of SuperCC's file, where the section is part of a setting's identity.)
- **Whitespace around `=` is trimmed**, on both the name and the value.
- **A duplicate name is not an error; the last one wins.**
- **Comments are whole-line only**, starting with `;` or `#`. There are no end-of-line comments —
  `legacyscores=true   ; roomy` has the value `true   ; roomy`, which is not `true`, so the setting
  stays off.
- **Unrecognized keys are preserved**, rewritten under an `[Other]` heading rather than dropped, so
  an older build cannot silently eat a newer build's settings.
- The file is **read once at startup and rewritten on a clean exit**, which means a hand edit takes
  effect on the next launch and an edit made while the game is running is overwritten.

## Consequences

- ⚠ **The file is in the WORKING DIRECTORY, not beside the executable.** Nothing in this tree
  resolves the executable's own path — there is no `GetModuleFileName`, no
  `QCoreApplication::applicationDirPath`, no `chdir`. `initdirs()` computes `root` as `$TWORLDDIR`,
  or `ROOTDIR` on a system build, or `"."`. "Beside the executable" is true only because
  double-clicking makes the working directory the program's folder. **Do not restate the stronger
  claim** — it was in the README, in two source comments and in a report before a review caught it.
- Launching from a different working directory silently gets a different settings file. When
  playtesting a scratch build, set the process's working directory to the scratch folder — that,
  not copying the executable, is what keeps a personal `tw_settings.ini` untouched.
- **Comments and blank lines are lost on rewrite.** The shipped stock file is generated by
  `package.ps1` and is where documented defaults live.
- A missing file is not an error; the program starts with defaults. Deleting it is the reset.
- Because the file is rewritten with only the settings actually held, a regenerated file is short.
  A missing line means "use the default".
